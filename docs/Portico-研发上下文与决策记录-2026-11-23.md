## 一、会话轮次归档


### 01. 从“多 Harness 管理”提出问题

**用户原话：**

> 我想你帮我调研下，现在是否有个产品可以读取本地的项目或者操作相关工具进行办公，例如我是一名IT，手上维护着多个项目，现在业务反馈跟我说某个系统出问题了，我就要到harness上打开这个项目让agent检查我的bug修复bug，然后发布。如果项目多了，我就要开多个harness进行处理，是否有个大的harness来管控这些小的harness。例如不是IT人员，我跟他们授权的某些项目，他们可以通过项目cli来问数 办公 等日常工作？
> 我思考现在ai智能题都是单独针对项目的，是否有包含公司所有系统的agent, 解脱原本工作流程，要打开多个系统，这里点一下，哪里查下数据，又在另一个地方编写报告。
> 你帮调研下 是否有类似项目？

**助手回复（整理）：**

**答复主旨（整理，非逐字）：** 将需求拆成两层：①统一 Coding Harness，自动识别代码仓库、日志与 CI/CD，排障、修复并提 MR；②企业级员工 AI 工作入口，依据员工权限跨 ERP、OA、CRM、数据平台查询和操作。提出“Enterprise Agent OS / Agent Control Plane”概念。

**当时列举的项目与方向：** Omnigent（Meta-Harness）、Paperclip（Agent 管理）、Raven、OpenHands、OpenAI Symphony、OpenClaw，以及 Glean、Moveworks、Onyx、WrenAI、n8n、Backstage。建议先利用现有 GitLab/Jenkins 与 OpenClaw 验证单入口调用多个代码项目；将只读问数和业务执行作为第二条路径。强调生产部署保持必要的 CI/CD 门禁，不应把“自动修复”与“未经检查自动上线”视为同一件事。

**阶段性结论：** 不必开发新的 Coding Harness，可用统一控制面 + 专业执行 Agent + 授权 Tool Gateway。


### 02. 讨论 Grok Bot 能否完成设想

**用户原话：**

> grok bot 是否也能完成我的设想项目？

**助手回复（整理）：**

**答复主旨（整理，非逐字）：** 将 Grok Bot 视为可用于验证云电脑、多 Bot 协作、本地文件/命令操作及跨工具办公的产品选项。为 IT 使用场景提出“总控 Bot → 运维/开发/发布 Bot → GitLab、Jenkins、日志、数据库”的协作分工；为普通员工设计共享业务 Bot。指出团队共享 Bot 并不等于业务数据逐用户授权；不建议多个员工使用一个高权限管理员凭据。

**重要限制：** 对云托管、自托管、账户隔离、价格、API 开放程度等结论均来自当轮资料讨论，尚未在用户环境部署核实。


### 03. 提出“真实组织架构 + 岗位 Agent”

**用户原话：**

> grok bot 是个聊天群，对于OPC 小公司确实适用，对于大企业有多个部门交互，有组织架构关系，是否可以做个组织架型的多agent,各个agent背后都有一个真实岗位的人，他能接收到相关信息，他来决定是否执行？如果执行这个agent就会去执行相关的任务

**助手回复（整理）：**

**答复主旨（整理，非逐字）：** 讨论“组织架构型 Multi-Agent / Human-in-the-Loop”模式：部门、岗位、真实员工与 Agent 模板分离；岗位责任人可接收执行提议，跨部门时 Agent 协作流转。提出任务审批卡、岗位代理、组织关系和项目权限应建模为不同关系。

**当时关注的方案：** Paperclip、Agentic Organization、AgentTeams、Agent-Staff，以及 Camunda、Temporal 作为人工任务与持久化流程的辅助组件。

**后续被用户修正：** 这种“遇事必审批”的模型增加了操作步骤，偏离提效初衷；此轮方案不是最终产品基线。


### 04. 关键转向：预授权自动执行，而非逐任务审批

**用户原话：**

> 如果又加入审批节点 有点本末倒置了，原本使用AI就是为了提效的，现在又卡再人这一步骤。每个用户给他们开启对于项目 对应的权限，他们可以问数可以办公。你觉得这种方式呢？这样对项目本身的封装要求就很高了

**助手回复（整理）：**

**答复主旨（整理，非逐字）：** 接受并确立“**一次授权、持续使用、按权限自动执行**”原则；由组织驱动的审批型 Agent 转为“**组织身份驱动的能力型 Multi-Agent**”。员工只需对统一入口下达任务；Master Agent 根据员工身份、角色、项目授权和数据范围，调用 ERP、CRM、GitLab 等工具。

**重要架构转变：** `员工 → 身份与权限上下文 → Master Agent → Tool Gateway → 业务能力适配层 → 现有系统`。项目不一定各自拥有独立 Agent；专业 Agent 负责推理，确定性业务操作应封装为 Tool。

**产品核心技术边界：** Capability Adapter、Capability Registry、API/MCP、服务端权限与行级数据约束、业务语义、幂等性、审计、版本管理。建议分 L1（接口接入）、L2（业务语义）、L3（Agent-Native）逐步改造。默认只读和低风险授权操作直接执行；涉及批量破坏性操作、生产发布等需按风险使用额外安全门禁，避免每次人工审批。


### 05. 产品命名及竞品调研

**用户原话：**

> 你说的对，确实**企业 AI 能力操作系统（Enterprise AI Capability OS）**  才有未来。那现在是否有类似的项目了呢？

**助手回复（整理）：**

**答复主旨（整理，非逐字）：** 确认产品定位为 **Enterprise AI Capability OS（ECAOS）**，不是通用聊天助手和“Agent 群聊”，重点是统一员工入口、动态权限、业务能力发现、跨系统任务。

**重点开源候选：** Archestra、Obot、IBM ContextForge（MCP Context Forge）、MCP Gateway & Registry、Onyx、Activepieces。

**对照商业方向：** OpenAI Frontier、MuleSoft Agent Fabric、Microsoft Agent 365、Glean。

**产品差异化：** 避免重造模型网关、MCP 网关和聊天应用。真正值得自研的是**传统企业系统的低成本 AI-Ready 改造能力**：REST API 转 MCP，统一 Capability Contract，业务语义与指标定义、员工数据范围映射、工具调用契约、幂等和版本兼容。协议 MCP 不等于完整的企业能力标准。

## 二、经过讨论确定的产品与架构基线

### 2.1 产品定位

- 名称：**企业 AI 能力操作系统 / Enterprise AI Capability OS（ECAOS）**。
- 价值主张：让企业现有系统按低成本标准化方式成为 AI 可发现、可授权、可执行的业务能力；让员工只用一个入口完成跨系统问数、办公和授权操作。
- 不做的事：不重新发明通用大模型、MCP 协议、通用聊天系统；不以“一人一个大模型 Agent”“一项目一个 Agent 群”为产品核心；不默认所有操作必须人工审批。
- 产品竞争策略：不与大型商业企业平台全面对抗，先攻传统 REST API / 旧系统接入及业务权限语义标准化。

### 2.2 最终分层架构

```text
用户：Web / 企业微信 / CLI / IDE
           ↓
统一员工身份、组织、角色、项目与数据权限
           ↓
ECAOS Master Agent / Task Router
           ↓
MCP Gateway / Capability Registry（候选：Obot）
           ↓
ECAOS 自研 Capability Adapter / Contract SDK
           ↓
ERP / CRM / OA / GitLab / Jenkins / 旧业务系统
```

- Master Agent 负责理解、检索能力、编排与汇总，不默认拥有超级管理员权限。
- 普通业务调用尽量直接调用确定性业务 Tool；复杂软件工程、分析和报告任务才委托专业 Agent。
- 数据权限由真实业务服务端强制执行；不能仅依赖 Tool 元信息或 Prompt 限制。
- 授权内的只读/低风险操作尽量直接执行；破坏性或生产级风险操作仍需服务端门禁。

### 2.3 自研核心资产

- Capability Contract：统一能力 ID、业务域、参数、返回值、数据范围、权限、side_effect、幂等性、版本和 owner。
- Adapter SDK：OpenAPI / REST 到 MCP 的标准适配，可兼容复杂认证、字段语义及错误映射。
- 企业业务语义：指标口径、实体关系、字段级/行级约束、项目权限映射。
- 能力发现：大量工具时动态检索并选取授权能力，不一次把全部工具塞入模型上下文。
- 质量治理：契约测试、权限回归测试、可追溯操作、版本兼容和故障恢复。

### 2.4 基础设施选型状态

| 对象 | 角色 | 结论 |
|---|---|---|
| Obot | 首选 MCP Gateway / 能力治理候选 | **优先做 PoC；尚未正式生产验证** |
| Archestra | 完整平台方案与用户体验对照 | 保留为备选，并参与 PoC 对比 |
| OpenClaw | 可作为早期统一 Agent 入口 | 不强制作为永久控制平面 |
| OpenHands/Codex | IT 代码分析与修复执行层 | 用安全工作区执行，不默认直接发布生产 |
| Temporal/Camunda | 需要持久化流程时的可选组件 | 第一阶段不引入强制逐项审批流程 |

### 2.5 MVP 范围和验收

1. ERP/类似业务系统：同一 Tool 给不同员工返回各自有权查看的数据；支持自然语言问数、汇总与报告。
2. IT 工具链：自然语言定位系统、查看日志、关联代码、运行 Agent 修复、测试并创建 Merge Request。
3. 跨系统调用：能识别并调用多个授权工具，完成分析与有限低风险写入。
4. 新系统接入：通过 Adapter SDK/Capability Contract 注册新能力，不改 Master Agent 核心代码。
5. 安全门禁：业务服务端拒绝越权读取、越权写入、超范围数据查询；幂等和审计可验证。
6. 底座 PoC：真实身份传递、权限累加、工具发现、内网部署、故障恢复及许可证合规为关键验证点。
