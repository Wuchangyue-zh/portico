# Portico

**Enterprise AI Capability OS · 企业 AI 能力操作系统**

*por·ti·co* /ˈpɔːrtɪkoʊ/ — 柱廊门廊。一座建筑只有一个正门，穿过它，才能抵达里面每一个房间。

`阶段：规划基线已冻结 · 底座 PoC 未启动 · 无生产代码`

</div>

---

## 一句话

Portico 把企业里那些彼此孤立的 ERP / CRM / OA / GitLab / Jenkins / 自研遗留系统，变成 **AI 可发现、可授权、可执行、可审计的能力**，让员工只用一个入口，完成跨系统的问数、办公和授权范围内的操作。

**卖点不在模型、不在协议、不在聊天界面**——而在传统系统的低成本 AI-Ready 改造：能力契约、可信适配层、业务语义与数据范围治理。

## 它不是什么

| 不是 | 为什么 |
|---|---|
| 又一个通用聊天助手 | 聊天只是入口形态，资产在能力层与治理层 |
| 「一人一个 Agent」/「一个项目一个 Agent 群」 | 常驻模型实例成本高、难复用；确定性业务操作应封装成 Tool |
| 重造 LLM / 重造 MCP / 重造向量库 | 这些轮子已经很好，再投入是浪费 |
| 每一步都要人工审批的工作流引擎 | 逐任务审批会把 AI 的效率优势全部抵消 |
| 又一个 MCP Gateway | 网关是候选底座，可以换；自研的是它上面的业务契约与适配层 |

## 架构

```text
  统一入口  Web / 企业微信 / CLI / IDE
      │
      ▼
  可信身份 · 组织 · 角色 · 项目 · 数据范围        ← 身份来自企业 IdP，不接受客户端自报
      │
      ▼
  Master Agent / Task Router                     ← 理解意图、检索能力、编排、汇总；默认不持超管权限
      │
      ├──────────────► 专业 Agent 沙箱           ← 只有推理 / 编码 / 长任务才实例化
      │                    │
      ▼                    ▼
  MCP Gateway · Capability Registry              ← 候选底座：Obot（Archestra 对照）
      │
      ▼
  Portico Capability Adapter / Contract SDK      ← 自研核心资产
      │
      ▼
  ERP / CRM / OA / GitLab / Jenkins / 遗留系统    ← 业务事实与最终数据权限仍在此
```

## 三条不可退让的原则

**1. 预授权自动执行，而不是逐任务审批。**
只读与低风险写入在授权范围内直接执行；人工确认只作为**高风险异常的安全边界**，不做成常规流程节点。

**2. 能做 Tool 就不上 Agent。**
单步确定性业务能力 → 直接调用工具；多步分析 → 编排多个工具；只有需要持续推理和改代码时才起专业 Agent。

**3. 双层授权，服务端硬校验。**
网关校验「你能不能调这个工具」，Adapter / 源系统校验「你能不能看这行数据、改这个字段」。任何 `user_id`、`tenant_id`、`region` 都不信任模型给的裸参数；未授权的能力**连被发现都不允许**。

> 由此推出的第 4 条：**业务事实与最终数据权限归源系统**（ADR-004）。平台不拿管理员数据库账号当作所有系统的统一入口。

## 自研 vs 复用

| 自研（核心资产） | 复用（可替换底座） |
|---|---|
| Capability Contract（能力契约规范） | MCP / LLM Gateway（Obot 候选，Archestra 对照） |
| Capability Adapter SDK（REST/OpenAPI → MCP） | 企业 IdP / SSO |
| 业务语义与指标口径、行级/字段级范围映射 | 容器编排、数据库、可观测性栈 |
| 动态能力发现（工具多时按权限检索，而非全量塞进上下文） | Coding Agent Runtime（Codex / OpenHands 等，隔离执行） |
| 契约测试 + 权限矩阵回归 | — |

明确边界：**协议（MCP）不等于企业能力标准。** Portico 定义的是 MCP 之上的业务元数据约定——版本、风险级别、副作用、幂等、数据范围、Owner 与审计策略。

## 里程碑

| 阶段 | 核心交付 | 退出条件 |
|---|---|---|
| M0 需求/可研 | 两个试点场景、源系统接口清单 | API / 权限可用性明确 |
| M1 底座对接 | 用 Obot 真实实例跑 P01–P12 | 阻断项通过，身份链闭环 |
| M2 能力平台 | 能力注册、Adapter、Tool Gateway、审计 | 8–12 个能力可注册调用 |
| M3 场景联调 | 业务问数与报告、低风险写入、IT 排障到 MR | 关键 E2E 通过 |
| M4 验收交付 | 安全/回归/性能、部署文档、试点报告 | 验收标准满足 |

**M1 的五个阻断项**：P01 两员工同能力不同数据 · P02 Profile 权限叠加 · P04 用户身份可信委派 · P06 绕过前端直调网关 · P12 许可证与商业交付。

底座已定为 Obot，这一轮不是选型比较，而是验证身份链能否闭环。已知风险是 Obot 的 OpenAPI Runtime 不支持调用人身份注入——补位方案是自研可信 Adapter（PoC 中已验证可行）。**若 P04 在真实 Obot 上无法闭合，才启动 Archestra 评估作为兜底。**

**MVP 边界**：单组织、2 个场景、8–12 个能力、10–12 周、2 名工程师。不自动发布生产，不做跨系统强事务（Saga / 补偿 + 显式标注部分成功）。

## 名字的由来

Portico 是古典建筑正立面的柱廊门廊：它是**唯一入口**，也是**通往内部每一个房间的过渡空间**。

这正好是这个项目要做的两件事——给员工一个统一入口，并在入口与房间之间，完成身份、授权与能力的转换。
